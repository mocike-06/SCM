综合项目：ESP32 蓝牙遥控器（LED + 继电器）

系列：ESP32 进阶 更新：2026-10-25

把前面学过的蓝牙 SPP 与 GPIO 控制组合成一个完整小项目：手机蓝牙串口助手发送文本指令，ESP32 按「行」解析后控制板载 LED 与继电器，并回传执行结果。本讲从零讲清为什么要设计帧格式、什么是状态机、协议表怎么对齐，是蓝牙+GPIO 综合应用的模板。

一、本课目标与前置知识

学完本课你能做到：

  • 设计一套最简单的文本协议（帧格式 = 命令字符串 + 换行符结尾）。
  • 用 String 缓冲区逐字符拼接蓝牙收到的字节，遇到换行就解析执行。
  • 把解析结果映射到 GPIO 输出（LED、继电器），并回 OK/ERR 给手机。

需要提前掌握的前置知识（对应学习路线阶段 5 收尾）：

  • 蓝牙 SPP 透传（esp32-bluetooth.html）：会用 SerialBT.read/available。
  • GPIO 输出（esp32-gpio.html）：会用 digitalWrite。
  • C 字符串比较：String 的 == 运算符或 strcmp。

本课会出现的新名词：帧格式（行协议）、状态机（拼接/解析/执行三态）、协议表、粘包、缓冲区清空、低电平触发继电器。

二、基础概念铺垫

1. 为什么要设计帧格式：裸字节流是「一锅粥」

生活类比：蓝牙给你的是源源不断的字节流，像有人对着水龙头连续吐字，没有标点。你不知道哪几个字是一条完整指令——必须自己定一个「句号」（换行符），看到句号才算一句话结束。

一句话定义：帧格式是通信双方约定的「消息边界规则」。本课用最简单的行协议：每条指令以 \n 或 \r 结尾，前面是大写英文字符命令，如 LED_ON\n。

例子：手机 App 发 "LED_ON\n"，ESP32 读到 \n 时才知道这是一条完整指令，再去拼前面那 6 个字符。

2. 状态机：拼接 / 解析 / 执行 三个阶段

生活类比：处理一条指令像接快递——先把零散包裹拼起来（拼接态），凑够一件了再拆箱验货（解析态），确认是什么货再搬到货架（执行态），然后清空收货区等下一件。

一句话定义：本项目的状态机（教材称有限状态机 FSM，Finite State Machine）= 用一个 String 缓冲区不断追加字符（拼接态），遇到换行符进入解析态（字符串比较），匹配到命令就执行 digitalWrite（执行态），最后清空缓冲区回到拼接态。FSM 的三要素：有限个状态、状态间按条件转移、每个状态下做固定动作——本课就是「拼接→解析→执行→拼接」的循环转移。

例子：inputString 不断 += c；遇到 \n 时 if/else 比较 "LED_ON"/"RELAY_ON" 等，然后 inputString = "" 清空。

3. 协议表：手机和单片机必须「对暗号」

生活类比：手机发什么、ESP32 做什么、回什么——三者必须事先写在一张表上对齐，像地下党对暗号：你说「天王盖地虎」，我必须回「宝塔镇河妖」，对不上就是自己人。

一句话定义：协议表是一张三列对照表：手机发送的命令字符串、ESP32 要执行的动作、ESP32 回包内容。任何一端改了命令字，另一端必须同步改。

例子：表里规定发 "LED_ON" → GPIO2=HIGH → 回 "OK: LED_ON"；发 "RELAY_OFF" → GPIO4=HIGH（低触模块断开）→ 回 "OK: RELAY_OFF"。

4. 粘包与缓冲区：不清空就会「串味」

生活类比：如果上一条指令处理完不清空缓冲区，下一条指令的字符会拼在上一条尾巴后面——像饭盒没洗就装新菜，味道全串了。

一句话定义：粘包指多条指令的字节混在同一个缓冲区里；解决方法是每处理完一条，立即 inputString = ""; 清空，等下一条从头拼。

例子：处理完 "LED_ON" 后不清空，下一个字符 "R" 会拼成 "LED_ONR"，再也匹配不到任何命令。

5. 低电平触发继电器：不是所有模块都「高电平干活」

生活类比：继电器模块像一个电磁开关——给信号脚一个电平，内部电磁铁吸合，把 COM 和 NO 两个端子接通。但有的模块「给低电平才吸合」（低触发），有的「给高电平才吸合」（高触发），看板上标签。

一句话定义：常见 5V 继电器模块多为低电平触发：IN 脚写 LOW 时吸合（COM-NO 接通），写 HIGH 时断开。代码里默认要把 IN 脚写 HIGH，避免上电瞬间乱吸合。

例子：digitalWrite(relayPin, LOW) 听到「嗒」一声吸合，负载通电；写 HIGH 断开。

三、原理介绍

本项目是对「蓝牙串口桥」的升级：不再把字节原样透传，而是按帧解析后执行动作。蓝牙链路本身只负责「搬字节」，真正的业务逻辑在单片机端完成。

一条指令从手机到执行的链路：手机 App 发一串字节 → 蓝牙缓冲区排队 → loop 逐字节拼进 String → 遇到换行判定「一条完整指令」→ 比对命令表 → 执行 digitalWrite → 回一句确认。

原理 1：为什么必须有「帧边界」——粘包问题

蓝牙/TCP 这类链路是字节流，不是「一条一条消息」：手机连发 LED_ON 和 RELAY_OFF，ESP32 可能一次 read 到 LED_ONRELAY_OFF 连在一起——这就是「粘包」。解法是双方约定一个边界符号：本协议用换行符 \n 当边界——没等到换行就一直拼在缓冲区，等到换行才把整串当一条指令解析。这就是为什么 App 发送设置里必须勾选「加 \n」：没有边界符，单片机永远不知道一条指令从哪结束。

原理 2：文本行协议 vs 二进制帧——各解决什么问题

本课用的是文本行协议：人能读懂、调试方便（串口打出来就是 LED_ON），代价是占字节多、没有校验——蓝牙链路偶尔出错拼错一个字母，就匹配不上任何命令。第二个实例演示的二进制帧协议（帧头 0xAA + 长度 + 数据 + 校验和）多花几个字节，换来「错包能被校验和丢弃、不会误执行」。工程上简单设备用文本行就够，工业遥控才上二进制帧+CRC。

原理 3：为什么要回一句 OK——半双工链路的确认

蓝牙链路是半双工：双方轮流说，没有硬件级确认机制。手机发完一条 LED_ON，如果蓝牙丢包了，手机端毫无察觉——灯没开、用户还以为开了。ESP32 每执行一条就 println("OK: LED ON") 回一句，手机收到回包才知道「这条真的送达并执行了」。一问一答 = 应用层的确认机制，这也是所有遥控协议（包括后面 MQTT 的 QoS）解决可靠性的核心思路。

记忆点：字节流会粘包，必须约定边界符（本课=\n）；文本行协议好调试但无校验，二进制帧+CRC 更可靠；一问一答回 OK 是应用层确认；协议表=手机发什么/ESP32 做什么/回什么，三者严格对齐。

四、硬件接线说明

除板载 LED 外，外接一路继电器模块，用它控制一盏台灯 / 风扇等低压或强电负载（强电部分请由有经验者接线，注意安全）。

模块引脚单片机引脚说明
板载 LEDLED_BUILTIN（GPIO2）板载已连，无需外接
继电器模块 IN（信号）GPIO4低电平触发 / 高电平触发视模块而定
继电器模块 VCC5V（VIN）多数继电器模块需要 5V 才能可靠吸合
继电器模块 GNDGND必须与 ESP32 共地
继电器 COM / NO外部负载吸合时 COM 与 NO 接通，可直接控制强电回路

为什么这样接：

  • 为什么继电器 VCC 接 5V 不是 3V3？ 继电器线圈驱动需要 5V，3.3V 往往吸合无力、发出异响；接 VIN（USB 5V）最可靠。
  • 为什么必须共地？ ESP32 和继电器模块的地不连，IN 脚的电平参考点不同，继电器会误触发。
  • 为什么 GPIO4 默认写 HIGH？ 低触模块上电瞬间 GPIO4 是输入态（电平悬空），可能误吸合；setup 里立刻 pinMode + 写默认 HIGH（断开），保证安全。
强电安全 继电器侧的 220V 接线务必断电操作，用螺钉端子压紧、套热缩管；不要在通电时触碰 COM/NO 端。演示阶段建议先用一个 5V 小电机 / LED 灯串验证。

/* ESP32 蓝牙遥控器：手机发文本指令控制 LED 与继电器（零基础注释版） */
#include "BluetoothSerial.h"

BluetoothSerial SerialBT;

const int ledPin   = 2;    // 板载 LED
const int relayPin = 4;    // 继电器信号脚（低电平触发）

String inputString = "";   // 指令拼接缓冲区

void setup() {
  Serial.begin(115200);
  pinMode(ledPin, OUTPUT);
  pinMode(relayPin, OUTPUT);
  digitalWrite(relayPin, HIGH);   // 低触模块：默认断开，防止上电误吸合

  SerialBT.begin("ESP32_Remote"); // 蓝牙广播名
  inputString.reserve(64);       // 预分配 64 字节，避免反复申请内存
  Serial.println("蓝牙遥控器就绪：ESP32_Remote");
}

void loop() {
  while (SerialBT.available()) {           // 把当前所有字节读完
    char c = SerialBT.read();
    // 遇到换行 / 回车，认为一条指令结束
    if (c == '\n' || c == '\r') {
      if (inputString.length() > 0) {       // 空行忽略
        Serial.print("收到指令：");
        Serial.println(inputString);

        if (inputString == "LED_ON") {
          digitalWrite(ledPin, HIGH);
          SerialBT.println("OK: LED_ON");
        } else if (inputString == "LED_OFF") {
          digitalWrite(ledPin, LOW);
          SerialBT.println("OK: LED_OFF");
        } else if (inputString == "RELAY_ON") {
          digitalWrite(relayPin, LOW);      // 低触模块吸合
          SerialBT.println("OK: RELAY_ON");
        } else if (inputString == "RELAY_OFF") {
          digitalWrite(relayPin, HIGH);     // 低触模块断开
          SerialBT.println("OK: RELAY_OFF");
        } else {
          SerialBT.println("ERR: unknown command");
        }
        inputString = "";                   // 清空缓冲区，准备下一条
      }
    } else {
      inputString += c;                     // 拼字符进缓冲区
    }
  }
}

第二个实例：二进制帧协议解析（帧头 0xAA + 长度 + 数据 + 校验和）——主程序是文本指令，这个变体演示状态机解析带校验的二进制帧，抗干扰更强：

/* remote 变体：帧协议状态机解析 */
#include "BluetoothSerial.h"
BluetoothSerial SerialBT;

enum { WAIT_HEAD, READ_LEN, READ_DATA, READ_CKS } state = WAIT_HEAD;
byte buf[16];
byte len = 0, idx = 0, cks = 0;

void setup() {
  Serial.begin(115200);
  SerialBT.begin("ESP32_BT");
}

void loop() {
  while (SerialBT.available()) {
    byte b = SerialBT.read();
    if (state == WAIT_HEAD && b == 0xAA) {   /* 帧头 0xAA */
      state = READ_LEN; idx = 0; cks = 0;
    } else if (state == READ_LEN) {
      len = b; state = READ_DATA;             /* 记下数据长度 */
    } else if (state == READ_DATA) {
      buf[idx++] = b; cks += b;               /* 收数据并累加校验 */
      if (idx >= len) state = READ_CKS;
    } else if (state == READ_CKS) {
      if (b == cks) Serial.printf("帧OK: %d\r\n", buf[0]);   /* 校验通过 */
      else          Serial.println("校验失败，丢弃");
      state = WAIT_HEAD;
    }
  }
}

想加高触发继电器？把 RELAY_ON/RELAY_OFF 里的 LOW/HIGH 对调即可；想加一条 STATUS 指令返回当前状态？在 else if 链里加一支即可。

六、代码逐段讲解

第 1 段：引脚定义与缓冲区（第 4~13 行）

在做什么： 定义 LED 和继电器引脚号，创建一个空字符串 inputString 作为指令缓冲区。

为什么这么写： 把引脚号提为常量，改硬件只改一行；inputString.reserve(64) 预先分配内存，避免 += 时反复申请释放导致碎片。

不写会怎样： 漏 reserve 也能跑，但长时间运行 String 容易内存碎片；漏 pinMode/默认电平，继电器上电瞬间可能乱跳。

第 2 段：setup() 默认安全态（第 15~23 行）

在做什么： 把 LED 和继电器引脚配成输出，继电器先写 HIGH（低触模块=断开），再开蓝牙广播。

为什么这么写： ESP32 上电瞬间 GPIO 是输入态，电平悬空，低触继电器可能因悬空电平被误触发；立刻 pinMode + 写默认 HIGH 是安全习惯。

不写会怎样： 一上电继电器就「嗒」一声吸合，接的台灯突然亮——有安全隐患。

第 3 段：loop() 读字节与状态机（第 25~51 行）

在做什么： while(SerialBT.available()) 把当前缓存的字节一次读完；遇到 \n/\r 就解析 inputString，否则继续 += 拼字符。

为什么这么写： 蓝牙字节可能一次来多个，用 while 循环一次性清空 available，避免漏读；用 \n/\r 做帧边界是行协议的核心。

不写会怎样： 用 if 而不是 while，蓝牙一次来多个字节时会丢后半；不判 \n 直接解析，命令永远拼不齐。

第 4 段：if/else 命令分发（第 30~45 行）

在做什么： 把缓冲区字符串和预设命令逐一 == 比较，匹配到哪条就执行对应的 digitalWrite 并回 OK；都不匹配回 ERR。

为什么这么写： String 的 == 运算符已经做了逐字符比较，比手写 strcmp 直观；回 OK/ERR 是「应答」，让手机知道命令有没有被收到。

不写会怎样： 不回包，手机发完没反馈，用户不知道命令有没有生效；不加 else 兜底，未知命令被静默忽略。

第 5 段：清空缓冲区（第 46 行）

在做什么： 处理完一条指令后立即 inputString = "" 清空。

为什么这么写： 不清空，下一条指令的字符会拼在上一条尾巴上，导致粘包、命令永远匹配不到。

不写会怎样： 发了几条后所有指令都变成 "LED_ONRELAY_OFF..." 这种串，全部回 ERR。

七、现象演示说明

  • 连接：手机蓝牙串口助手连接 ESP32_Remote，发送选项务必勾选「发送新行（\n）」。
  • 验证 LED：发送 LED_ON，板载 LED 点亮，手机收到 "OK: LED_ON"；发送 LED_OFF，LED 熄灭。
  • 验证继电器：发送 RELAY_ON，听到继电器「嗒」一声吸合，外接负载通电；发送 RELAY_OFF，负载断电。
  • 验证异常：随便发 ABC，ESP32 回 "ERR: unknown command"，且不改变任何引脚状态。

可量化的验证方法：

  • 数回包：发 5 条合法指令，手机应恰好收到 5 条 "OK: ..." 回包；发 1 条非法指令，收到 1 条 "ERR: ..."。
  • 粘包测试：快速连发 "LED_ON\nLED_OFF\n"，应依次回两条 OK，LED 先亮后灭——验证状态机能处理连续帧。
  • 扩展思路：把这套解析逻辑搬到 MQTT 的 callback 里，就成了「手机 App 通过互联网远程控制家电」，协议层完全不用改。

九、课后练习与延伸

练习 1（加 STATUS 指令）： 手机发 "STATUS"，ESP32 回当前 LED 和继电器状态，如 "LED=ON, RELAY=OFF"。提示：在 else if 链里加一支，用 digitalRead 读回引脚电平。

练习 2（加 PWM 调光）： 把 LED 改成 PWM 呼吸灯，发 "DIM:128" 之类的命令设置亮度。提示：用 String::indexOf 找到 ':' 再用 toInt() 解析数字。

练习 3（迁移到 MQTT）： 把这套解析逻辑从蓝牙 SerialBT 搬到 MQTT 的 callback 里，让手机通过互联网（而不是近距离蓝牙）控制继电器——这就是智能家居的雏形。
