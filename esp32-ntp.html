NTP 网络校时（设备日历时钟）

系列：ESP32 进阶 更新：2026-10-25

物联网设备的日志时间、定时上报、数据点时间戳——都要「真实时间」。但 ESP32 上电不知道今天是几号：得连上 WiFi 问网络。NTP 就是「网上的授时服务」：问一次拿到标准时间，之后靠内部计时器走。本课讲透 NTP 原理、UTC/本地时间、时区概念，用 ESP32 实现「上电自动对时 + 串口报时 + 断网也能走」的设备时钟。

一、本课目标与前置知识

学完本课你能做到：

  • 说清 NTP 是什么、为什么要先连 WiFi 才能对时。
  • 理解 UTC 与本地时间/时区的换算（含夏令时）。
  • 用 ESP32 的 configTime/getLocalTime 做出能报时、能记时间戳的时钟。

需要提前掌握的前置知识（对应学习路线阶段 5）：

  • WiFi（esp32-wifi.html）：NTP 必须先联网。
  • 串口（esp32-bluetooth.html 或基础篇）：打印时间。
  • 可选：STM32 RTC（stm32-rtc.html）对比「芯片日历 vs 网络时间」。

本课会出现的新名词：NTP、UTC、时区、epoch（Unix 时间戳）、configTime、getLocalTime、time()、struct tm、夏令时。

二、基础概念铺垫

1. NTP 是什么：设备的「对表服务」

生活类比：NTP 就像广播电台的整点报时：设备连上网络，向授时服务器（如 ntp.aliyun.com、pool.ntp.org）问一句「现在几点」，服务器回一个标准时间戳。设备把它设为自己的当前时间。

一句话定义：NTP（网络时间协议）通过 UDP 从授时服务器获取 UTC 时间，精度可达毫秒级（局域网）/数十毫秒（公网）。ESP32 的 configTime() 封装了「问时间 + 设本地时钟」。

例子：上电后调用 configTime，几秒内 time(nullptr) 就能返回正确的 Unix 时间戳。

2. UTC 与时区：全世界共用一个「基准钟」

一句话定义：UTC（协调世界时）是全世界统一的时间基准（伦敦时间的近似）。各国本地时间 = UTC + 时区偏移：北京 = UTC+8（东八区）。NTP 只给 UTC，本地时间由设备自己加时区——configTime 里指定 "UTC+8" 或 "CST-8" 就是让系统自动换算。

例子：UTC 12:00 时，北京本地 = 20:00。程序里 tm 结构体的 tm_hour 在配好时区后就是本地小时。

3. epoch 时间戳：设备内部的时间「编号」

一句话定义：Unix 时间戳（epoch）= 自 1970-01-01 00:00:00 UTC 起经过的秒数（uint32，2038 年溢出）。设备内部存的是这个秒数，显示时再转成「年月日时分秒」（struct tm）。time_t 是秒数，localtime() 转本地日历。

例子：2026-10-25 12:00 UTC 的 epoch ≈ 1793001600；日志里存它最省空间、最标准。

4. 掉电后时间还准吗：RTC 硬件 vs 软件

一句话定义：ESP32 片内有 RTC 计时器：上电对时后，掉电（模块供电时）期间由内部 RTC 继续走；完全断电后时间丢失，下次上电需要重新 NTP 对时。对策：把最近一次时间戳存进 NVS（esp32-storage.html），重启后先用它凑合，再异步对时校正。

例子：断电 3 天再上电，程序显示的是「上次保存的时间」，联网后 2 秒内跳回真实时间。

5. NTP 在协议栈里的位置：应用层走 UDP

生活类比：和 MQTT 一样，NTP 也是应用层协议——它坐在 UDP 传输层肩膀上。区别是 MQTT 走 TCP（要可靠送达），NTP 走 UDP（一问一答，丢一包下次再问就行，不重传省延迟）。

一句话定义：按 TCP/IP 五层模型——WiFi 链路层、IP 网络层、UDP 123 端口传输层、NTP 应用层。NTP 用 UDP 而非 TCP，是因为校时追求低延迟，且丢一个请求包下一秒重发即可，不需要 TCP 的可靠连接开销。

例子：本课 configTime(..., "ntp.aliyun.com") 内部就是 lwIP 协议栈的 SNTP（简单 NTP）客户端发 UDP 包到服务器 123 端口——ESP32 跑的是简化版 SNTP，够嵌入式设备用。

三、原理介绍：从「问时间」到「会报时」

ESP32 片内没有电池供电的 RTC——断电后时间就丢了。NTP 让设备每次上电都从网络「问」一次标准时间。理解它「问的是 UTC、本地时间靠时区偏移换算、内部靠 epoch 秒数走时」这三层，才能搞懂 configTime 三个参数和 tm_year+1900 这些怪写法。

一次对时的链路：联网 → configTime 配置 → 后台发 NTP 请求拿 UTC 秒数 → 设为系统时间 → getLocalTime 按时区转成本地日历。

原理 1：NTP 报文——UDP 请求/响应，问的是 UTC 不是北京时间

NTP 用 UDP 123 端口：设备发一个 48 字节的请求包给授时服务器，服务器回一个包，包里带的是UTC（协调世界时，伦敦时间）的当前时刻。网络往返有几十~几百毫秒延迟，协议内部还会估算并补偿它，公网精度也能到几十毫秒。关键认知：NTP 只发 UTC，世界各地设备拿到的是同一个基准——「几点几分」由每个设备自己加时区换算。

原理 2：configTime 三个参数——时区偏移到底是什么

configTime(gmtOffset_sec, daylightOffset_sec, "ntp.aliyun.com")：第一个参数是本地区相对 UTC 的秒数偏移——北京东八区就是 8×3600=28800 秒；第二个是夏令时偏移（中国不实行夏令时，填 0）。系统拿到 UTC 秒数后，自动加上这个偏移存为「本地时间」，所以之后 getLocalTime 出来的 tm_hour 直接就是北京时间。为什么 configTime 调一次就够：lwIP 协议栈内置了 SNTP 客户端，它会按默认周期（约 1 小时）自动再对时，你不用自己轮询。

原理 3：epoch 秒数与 struct tm——内部怎么存「年月日」

设备内部存的其实不是「2026-10-25 14:30」这种字符串，而是一个 Unix 时间戳（epoch）：自 1970-01-01 00:00:00 UTC 起经过的秒数。time(nullptr) 返回它。要显示成人能读的日历，才由 getLocalTime 把秒数换算成 struct tm——所以 tm_year 要 +1900（它存的是「从 1900 起的年数」）、tm_mon 要 +1（它 0 表示一月）。存日志用 epoch 最省空间、最标准；显示才转日历。完全断电时间会丢——RTC 靠模块供电走时，USB 拔了就停，所以重启要重新 NTP 对时（可先用 NVS 存的旧 epoch 凑合）。

记忆点：NTP=UDP 问服务器拿 UTC 秒数（自带延迟补偿）；configTime(时区秒偏移, 夏令时, 服务器) 一次配置、后台周期自动校时；北京=UTC+8=28800 秒；内部存 epoch 秒数，tm_year+1900/tm_mon+1 才能显示；断电即丢，重启重对。

四、硬件接线说明

NTP 是纯软件 + 网络功能，无额外接线：

资源用途说明
ESP32 开发板联网 + 对时 + 打印USB 供电 + 串口监视器
路由器/热点提供网络连接可访问外网的 WiFi
（可选）OLED显示当前时间结合 esp32-i2c.html 做「桌面电子钟」

为什么必须能连外网：NTP 服务器在公网；纯局域网（无外网）环境要自建 NTP 服务器（如路由器自带或树莓派）并改成内网域名/IP。

避坑 校园网/公司网若做了「认证门户」（要网页登录）或封了 UDP 123 端口，NTP 会一直失败——先用电脑 ping ntp.aliyun.com 测试网络通不通，再查端口策略。串口里一直打印 1970 年就是典型症状。

五、完整代码

NTP 对时 + 串口报时（含连接状态与失败重试）

/* NTP 网络校时：上电自动对时，每秒打印本地时间 */
#include <WiFi.h>
#include <time.h>

const char *ssid     = "你的WiFi";      /* 改成你的 WiFi */
const char *password = "你的密码";

/* 东八区：UTC+8，无夏令时（中国不实行） */
const long  gmtOffset_sec = 8 * 3600;       /* 8 小时秒数 */
const int   daylightOffset_sec = 0;         /* 夏令时偏移 0 */

void connect_wifi(void)
{
    Serial.print("Connecting to WiFi");
    WiFi.begin(ssid, password);
    while (WiFi.status() != WL_CONNECTED) {
        delay(500);
        Serial.print(".");
    }
    Serial.println(" OK");
}

void sync_ntp(void)
{
    /* 配置授时：阿里云 NTP 服务器，后台自动周期校时 */
    configTime(gmtOffset_sec, daylightOffset_sec, "ntp.aliyun.com");

    /* 等待时间就绪：time() 返回非 0 即成功（最多等 10 秒） */
    int retry = 20;
    while (time(nullptr) < 100000 && retry-- > 0) {
        Serial.println("waiting NTP...");
        delay(500);
    }
}

void print_time(void)
{
    struct tm now;
    if (getLocalTime(&now)) {
        Serial.printf("%04d-%02d-%02d %02d:%02d:%02d\r\n",
                      now.tm_year + 1900, now.tm_mon + 1, now.tm_mday,
                      now.tm_hour, now.tm_min, now.tm_sec);
    } else {
        Serial.println("time not ready");
    }
}

void setup() {
    Serial.begin(115200);
    connect_wifi();
    sync_ntp();
}

void loop() {
    print_time();          /* 每秒报一次本地时间 */
    delay(1000);
}

进阶：断电续走——先读 NVS 旧时间，再异步对时

/* 断电恢复时间：重启先用上次存的 epoch，联网后自动校正
   依赖 Preferences（esp32-storage.html 已学） */
#include <WiFi.h>
#include <time.h>
#include <Preferences.h>

Preferences prefs;

void setup() {
    Serial.begin(115200);

    prefs.begin("clock", false);
    time_t saved = prefs.getLong("epoch", 0);
    if (saved > 100000) {
        struct timeval tv = { .tv_sec = saved, .tv_usec = 0 };
        settimeofday(&tv, nullptr);      /* 先用旧时间启动 */
        Serial.println("restored old time");
    }

    WiFi.begin("你的WiFi", "你的密码");
    configTime(8 * 3600, 0, "ntp.aliyun.com");
    /* 联网对时成功后 lwIP 自动更新系统时间，无需手动 set */
}

void loop() {
    time_t now = time(nullptr);
    /* 每小时存一次当前 epoch 到 NVS（掉电后恢复用） */
    static time_t last_save = 0;
    if (now - last_save > 3600) {
        prefs.putLong("epoch", now);
        last_save = now;
    }
    delay(1000);
}

六、代码逐段讲解

第一段：gmtOffset_sec 与 daylightOffset_sec

8 * 3600 把「8 小时」换成秒（UTC+8）；daylightOffset_sec = 0 因为中国不实行夏令时。如果设备在美国/欧洲：夏季要多加 1 小时（3600），且要按日期切换——configTime 只支持固定偏移，复杂夏令时要用 TZ 字符串（如 "CST-8" 之外还有 "EST5EDT"）。为什么中国直接 0：中国 1986 年后取消夏令时，固定 UTC+8。

第二段：time(nullptr) < 100000 的等待条件

epoch 大于 10 万 ≈ 1973 年以后：1970-01-01 的 epoch 是 0，未对时前系统时间就是 0（或很小的值）。用 time(nullptr) < 100000 判断「还没对时成功」——标准技巧。为什么不直接判 0：系统上电后有个极小的时间基数，判 0 可能误判。等待循环加超时（20×500ms=10s）防死等。

第三段：getLocalTime 与 tm 结构体的坑

now.tm_year + 1900：tm_year 从 1900 年偏移（2026 → 126）；now.tm_mon + 1：月份 0 起（1 月 = 0）。打印时忘了 +1900/+1 会显示 1126 年或 0 月——这是报时程序的经典 bug。

第四段：settimeofday 恢复旧时间

settimeofday 手动设置系统时间（秒+微秒）；把 NVS 里存的旧 epoch 写进去，设备启动瞬间就有「昨天的时间」。联网后谁把它改对：lwIP 的 SNTP 客户端对时成功会自动更新系统时间——你只管存旧值，校正交给系统。为什么每小时存一次：掉电最多丢 1 小时精度；存太频繁伤 NVS 寿命。

七、现象演示与验证

  • 对时成功：串口 Connecting to WiFi OK → 1~2 秒后打印 2026-10-25 14:30:05，秒数递增。
  • 时间正确性：与手机时间对照，误差应在 1 秒内。
  • 断电恢复：示例 2 断电 1 分钟重启，先打印旧时间，联网后自动跳回真实时间。

验证方法：

  1. 把服务器改成 "time.windows.com"（海外），对比对时结果——验证不同服务器可用性。
  2. 把 gmtOffset 改成 0，打印变成 UTC 时间（比北京时间早 8 小时）——验证时区换算。
  3. 拔掉路由器 WAN 口（断外网）重启设备：报时停在 1970 年——验证「必须能访问 NTP」。

九、课后练习与延伸
