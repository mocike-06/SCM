独立看门狗 IWDG

系列：STM32 进阶 更新：2026-10-25

程序「跑飞」——死循环、指针错乱、堆栈溢出——嵌入式系统里一旦发生，设备就变砖头，直到人手动断电。看门狗就是芯片内置的「自动重启保安」：你必须在规定时间内向它报到（喂狗），一旦超过时间它没等到，就强制复位整个芯片。本课讲透 IWDG 的时钟、预分频、重载值与喂狗写法。

一、本课目标与前置知识

学完本课你能做到：

  • 说清看门狗的原理：为什么「没喂狗就复位」能救程序。
  • 算清 IWDG 的超时时间：LSI 40kHz × 预分频 × 重载值。
  • 写出带看门狗的 main 循环：初始化、喂狗、避坑（不能喂太早/太晚）。

需要提前掌握的前置知识（对应学习路线阶段 4）：

  • 时钟概念（stm32-clock.html）：IWDG 用独立的低速时钟 LSI，不依赖系统时钟。
  • 寄存器操作（stm32-register.html）：IWDG 的预分频/重载都是寄存器配置。
  • 基本主循环结构（任意一篇外设教程）：看门狗就嵌在主循环里喂。

本课会出现的新名词：看门狗、喂狗（Kick/Reload）、IWDG、LSI 时钟、预分频、重载寄存器、超时时间、窗口看门狗 WWDG、独立 vs 窗口。

二、基础概念铺垫

1. 看门狗是什么：芯片的「自动重启保安」

生活类比：养了一条必须定时投喂的狗——你每隔一段时间必须喂它一次（喂狗），如果超时没喂，它就狂吠并触发「按重启键」（复位芯片）。程序正常时主循环一路顺畅，每次循环都喂得到；程序卡死在某个角落，喂狗语句执行不到，狗就咬下重启。

一句话定义：看门狗（Watchdog）是芯片内部的独立计数器：程序必须在设定时间内周期性「喂狗」（重载计数），否则计数器溢出触发系统复位。它是程序跑飞、死循环时自动恢复的硬件保险。

例子：产品现场的工控板若程序死锁，没人去断电——看门狗会在 1 秒后自动复位，设备自己缓过来。

2. IWDG 的两个关键参数：预分频与重载值

生活类比：IWDG 计数器像一个倒计时沙漏：预分频决定「一粒沙代表多久」（分频倍数），重载值决定「沙漏里有多少沙」。两者相乘 = 超时时间。

一句话定义：IWDG 用独立低速时钟 LSI（约 40kHz，不依赖主时钟、独立供电，主时钟挂了它还能跑）。超时时间 = LSI 周期 × 预分频 × 重载值。例：预分频 64、重载值 625 → 40kHz/64 = 625Hz → 每计数一次 1.6ms → 625 × 1.6ms ≈ 1 秒超时。

例子：IWDG->PR = IWDG_PRESCALER_64; IWDG->RLR = 625; 得到约 1 秒的喂狗期限。

3. 喂狗函数：向保安报到

一句话定义：喂狗 = 把重载值重新写进计数器，让倒计时从头开始。HAL 写法：HAL_IWDG_Refresh(&hiwdg)（等价于 IWDG->KR = 0xAAAA）。喂狗点应该放在主循环里「一定能执行到」的位置——通常是主循环开头或结尾，且喂狗周期必须小于超时时间。

例子：超时 1 秒，主循环每圈耗时 100ms，那就每圈喂一次（安全余量 10 倍，非常稳）。

4. 独立看门狗 vs 窗口看门狗

一句话定义：IWDG（独立看门狗）：独立时钟、超时范围大（几十 ms~几 s）、只管「别超时」，简单可靠，入门首选；WWDG（窗口看门狗）：挂 APB1 时钟，要求必须在特定时间窗口内喂（太早太晚都复位），能检测「程序跑得太快」的异常，更严格但难调。

例子：产品防死机用 IWDG 就够；对时序要求苛刻的场景（如主循环频率必须稳定）才需要 WWDG。

三、原理介绍：IWDG 的工作过程与初始化步骤

看门狗是一个「你不喂它、它就把芯片复位」的独立倒计时器。它的全部设计都围绕一个目的：程序跑飞时能自己救回来。

整条链路：LSI 40kHz → 经 PR 预分频 → 喂狗时把 RLR 装入递减计数器 → 数到 0 没等到下一次喂狗 → 触发系统复位。

原理 1：递减计数器——超时时间怎么算

IWDG 内部是一个从 RLR 往 0 数的递减计数器，时钟来自独立的 LSI ≈40kHz，再经 PR 预分频。超时 = (1/LSI) × 预分频 × (RLR+1)。HAL_IWDG_Refresh()（写 KR=0xAAAA）就是把 RLR 重新装回计数器、把倒计时「清零重来」——这就是「喂狗」。程序若正常，主循环每圈都喂、计数器永远数不到 0；若死循环卡死，没人喂，数到 0 就复位。

原理 2：为什么用独立 LSI，而不挂主时钟

看门狗的使命是在主程序连主时钟都可能挂掉时仍能复位芯片。若它也挂在 PLL/HSE 上，晶振一停它自己也停，就失去「最后防线」意义。LSI 是芯片内部 RC 振荡器，独立于主时钟——哪怕 PLL 跑飞、HSE 停振，它照样倒计时、照样复位。这就是「独立看门狗」名字里「独立」二字的含义。

原理 3：写保护与喂狗位置——为什么参数改不动、喂在哪

IWDG 的 PR/RLR 默认写保护，要先写 KR=0x5555 解锁才能配；启动用 0xCCCC。为什么要写保护：看门狗一旦启动几乎不能关（只有复位才重配），写保护防止代码某处误改超时参数，让它要么失效、要么立刻复位——这是刻意的「反悔困难」。喂狗点要放在所有主循环必经路径上、间隔小于超时；但不能在阻塞操作内部喂，否则那个阻塞卡死时照样喂狗，看门狗就形同虚设、把 bug 掩盖了。

记忆点：IWDG=LSI 40k 独立倒计时，超时=(1/40k)×预分频×(RLR+1)；0xCCCC 启动、0x5555 解锁、0xAAAA 喂狗；用独立时钟=主时钟挂了它还能救；喂狗在主循环必经、不能在阻塞里喂。

原理 4：IWDG 寄存器 ↔ HAL 函数对照（教材查表）

你做的事对应寄存器 / 键值HAL 函数
启动看门狗KR 写 0xCCCC（关键字启动）HAL_IWDG_Init() 内部自动启动
解锁写保护KR 写 0x5555（允许改 PR/RLR）HAL_IWDG_Init 内部解锁
设预分频PR 寄存器（0=/4, 1=/8 … 6=/256）hiwdg.Init.Prescaler = IWDG_PRESCALER_64
设重载值RLR 寄存器（0~0xFFF）hiwdg.Init.Reload = 625
喂狗（重载计数器）KR 写 0xAAAA（重装 RLR）HAL_IWDG_Refresh(&hiwdg)

为什么 IWDG 不挂 APB1：它由独立的 LSI(≈40kHz) 驱动，不属于任何 AHB/APB 总线外设，所以不需要 RCC 里的 APB 时钟使能位——这也是它「主时钟挂了还能跑」的硬件基础。

四、硬件接线说明

IWDG 是芯片内部功能，无需外部接线。需要的硬件只有观察手段：

模块接线说明
LED（验证复位）板载 LED（如 PC13）上电翻转一次，观察「复位后 LED 状态变化」
串口（可选）PA9/PA10打印复位原因与喂狗状态
按键（可选）PA0 接 GND模拟「卡死」场景（进入死循环）

为什么不需要给看门狗接线：IWDG 完全在芯片内部（独立时钟 + 计数器 + 复位逻辑），没有引脚。接线只是用来「观察现象」：LED 上电翻转一次 → 若复位发生，LED 状态会再次变化（如灭 → 亮 → 灭），串口可打印 __HAL_RCC_GET_FLAG(RCC_FLAG_IWDGRST) 确认是看门狗复位。

避坑 Keil 调试（仿真）时看门狗会真实计时，断点停住不喂狗也会触发复位，导致「单步调试时程序莫名重启」——调试带看门狗的工程时，要么先禁用 IWDG，要么加快喂狗频率，这是教材反复提示的调试坑。

五、完整代码

CubeMX 配置要点：勾选 IWDG，Prescaler = 64、Reload = 625（约 1 秒超时）。示例 1 标准喂狗；示例 2 故意不喂演示复位。

示例 1：带看门狗的主循环（正常喂狗）

/* IWDG 看门狗：主循环周期喂狗，程序卡死自动复位 */
#include "main.h"

extern IWDG_HandleTypeDef hiwdg;

void main_loop_work(void)
{
    /* 假设这里是真正的工作：读传感器、更新显示等，耗时约 100ms */
    HAL_Delay(100);
}

int main(void)
{
    HAL_Init();
    SystemClock_Config();
    MX_GPIO_Init();
    MX_IWDG_Init();             /* 启动看门狗：超时约 1 秒（PR=64, RLR=625） */

    while (1)
    {
        main_loop_work();       /* 正常工作 */

        /* 喂狗：必须在超时（1 秒）内执行到 */
        HAL_IWDG_Refresh(&hiwdg);
    }
}

示例 2：模拟程序卡死（演示看门狗复位）

/* 演示：卡死 + 不喂狗 → 1 秒后 IWDG 复位芯片 */
#include "main.h"

extern IWDG_HandleTypeDef hiwdg;

int main(void)
{
    HAL_Init();
    SystemClock_Config();
    MX_GPIO_Init();
    MX_IWDG_Init();

    /* 上电动作：翻转 LED 一次（可观察复位后的再次翻转） */
    HAL_GPIO_WritePin(GPIOC, GPIO_PIN_13, GPIO_PIN_RESET);
    HAL_Delay(300);
    HAL_GPIO_WritePin(GPIOC, GPIO_PIN_13, GPIO_PIN_SET);

    /* 故意卡死：进死循环，永不喂狗 */
    while (1)
    {
        /* 什么都不做 —— 约 1 秒后看门狗超时，芯片自动复位，
           程序回到 main 开头重新跑，LED 又翻转一次 */
    }
}

六、代码逐段讲解

第一段：MX_IWDG_Init 到底配置了什么

CubeMX 生成的 MX_IWDG_Init() 内部：hiwdg.Instance = IWDG; hiwdg.Init.Prescaler = IWDG_PRESCALER_64; hiwdg.Init.Reload = 625; 然后 HAL_IWDG_Init(&hiwdg)——它做了「启动 + 解锁 + 写 PR/RLR + 重载」全套。为什么 Prescaler=64、Reload=625：LSI≈40kHz ÷64 = 625Hz → 每个计数 1.6ms → 625 次计数 = 1.0 秒超时。改参数就是改超时时间，公式记牢。

第二段：喂狗点放在主循环「尾部」

HAL_IWDG_Refresh(&hiwdg) 放在每圈工作之后。为什么放尾部而不是开头：放开头意味着「上一圈哪怕卡死在工作里，这一圈也喂了」——不，实际上卡死就进不了下一圈，开头尾部没区别；真正重要的是它必须在所有路径的必经点。放尾部只是习惯，确保「工作做完才喂」。

第三段：示例 2 的观察逻辑

LED 上电先灭 300ms 再亮，然后程序卡死。为什么这样能看到复位：1 秒后 IWDG 复位，程序回到 main 开头，又执行「灭 300ms → 亮」——于是 LED 出现「亮 → 灭 → 亮」的重复，肉眼可见地「自己重启了」。验证方法：在 Keil 里加断点于 main 开头，每次复位都会命中断点。

七、现象演示与验证

  • 示例 1 正常现象：LED 无异常，程序稳定运行（每 100ms 工作 + 喂狗）。
  • 示例 2 复位现象：LED 亮起后约 1 秒熄灭再亮——芯片被看门狗复位，程序自动重启。

验证方法：

  1. 串口打印 __HAL_RCC_GET_FLAG(RCC_FLAG_IWDGRST)，复位后应为 SET——确认是 IWDG 复位而非上电复位。
  2. 把 Reload 从 625 改成 3125（约 5 秒超时），观察复位间隔从 1 秒变 5 秒——验证超时公式。
  3. 把喂狗间隔故意加大（主循环 HAL_Delay(1500) 超过 1 秒），示例 1 也会不断复位——理解「喂得太慢 = 会被咬」。

八、常见报错排查方案

报错现象可能原因解决方法
程序一上电就反复重启初始化后没喂狗 / 超时太短（如 50ms）主循环里及时 Refresh；Reload 与分频按需加大
单步调试时程序莫名重启断点停住时看门狗在计时调试时先注释 IWDG_Init，或用仿真器禁狗功能
喂狗了还重启喂狗点不在所有路径上 / 某分支耗时超时把 Refresh 移到循环必经点；检查最长分支耗时 < 超时
改了 PR/RLR 但没效果没解锁（KR=0x5555）或改错寄存器用 HAL_IWDG_Init 配置，别直接写寄存器；核对 CubeMX 参数
看门狗无法关闭IWDG 一旦使能只能复位后重配想关：烧录时用「不初始化 IWDG」的工程覆盖即可
掉电重启后状态不对复位原因没区分（上电 vs 看门狗）用 RCC 复位标志区分，异常复位时做数据恢复

九、课后练习与延伸

练习 1（必做）：用公式算三组超时时间（PR=16/RLR=100、PR=64/RLR=625、PR=128/RLR=1000），分别烧录验证复位间隔。

练习 2：在示例 1 的 main_loop_work 里人为写一个 while (1); 死循环，观察看门狗 1 秒后复位——亲手制造并观察「程序跑飞自救」。

练习 3（进阶）：读一下 RCC 时钟教程 的复位标志，写一段代码区分「上电复位 / 看门狗复位 / 按键复位」，串口打印原因，做一个工业级的启动诊断。
