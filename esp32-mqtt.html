MQTT 接入物联网：发布与订阅

系列：ESP32 进阶 更新：2026-10-25

在 WiFi 联网基础上引入 MQTT 协议，让 ESP32 连到公共 Broker，既能主动上报数据，也能远程接收下行指令。本讲从零讲清 Broker/Topic/QoS/发布订阅模型、PubSubClient 库怎么用、回调函数为什么是「别人替你调用」，是智能家居与工业物联网最常用的通信模型。

一、本课目标与前置知识

学完本课你能做到：

  • 理解 MQTT 发布/订阅模型：设备不直接对话，通过 Broker 中转。
  • 用 PubSubClient 库连上公共 Broker，向某个 Topic 发布消息、订阅某个 Topic 收消息。
  • 会写回调函数处理下行指令，会断线自动重连。

需要提前掌握的前置知识（对应学习路线阶段 5）：

  • WiFi STA 模式（esp32-wifi.html）：ESP32 能联网、能拿到 IP。
  • C 语言函数指针概念（不强求理解，会用回调即可）。
  • 电脑上能装一个 MQTT 调试工具（如 MQTTX）用于验证上下行。

本课会出现的新名词：MQTT、Broker（消息代理）、Topic（主题）、QoS、发布（publish）、订阅（subscribe）、PubSubClient、回调函数（callback）、客户端 ID、心跳保活。

二、基础概念铺垫

1. MQTT 与 Broker：像「邮局」而不是「对讲机」

生活类比：HTTP 像两个人直接打电话——你拨我号码，我接，聊完挂。MQTT 像邮局：你不直接和对方说话，而是把信扔进某个信箱（Topic），邮局（Broker）负责把信转投给所有订阅了这个信箱的人。设备之间根本不知道对方存在。

一句话定义：MQTT（Message Queuing Telemetry Transport）是一种轻量级发布/订阅协议，专为低带宽、不稳定网络下的物联网设备设计；Broker 是中间的消息服务器，负责中转所有消息。

例子：ESP32 向「esp32/test」发 "hello"，手机 App 只要订阅了「esp32/test」就能收到——两者从没直接连过。

2. Topic（主题）：分层的「信箱地址」

生活类比：Topic 像一个分层地址，用斜杠分隔，如 home/livingroom/temperature——你可以订阅整个「home/#」收下所有房间数据，也可以只订「home/livingroom/#」只看客厅。

一句话定义：Topic 是形如 esp32/test 的层级字符串，用斜杠分层，支持通配符 +（单层）和 #（多层）。

例子：ESP32 每 5 秒向 esp32/test publish 一条 "hello"，同时订阅 esp32/cmd；手机 App 向 esp32/cmd 发 "on"，ESP32 的回调就被触发。

3. QoS：消息的「投递等级」

生活类比：QoS 像快递的保价方式——0 级是普通平信（丢了也不重发），1 级是挂号信（至少到一次），2 级是签收回执（严格一次）。等级越高越可靠但越费流量。

一句话定义：QoS（Quality of Service）分 0/1/2 三档，决定 Broker 与客户端之间如何保证消息送达。IoT 入门默认用 QoS 0 即可。

例子：本课 client.subscribe("esp32/cmd") 默认 QoS 0，对学习演示足够；正式产品的控制指令建议用 QoS 1。

4. PubSubClient：把 TCP/MQTT 握手全包了

生活类比：手写 MQTT 协议要处理 TCP 连接、握手、心跳、分包，像自己造发动机。PubSubClient 库是别人造好的发动机，你只管转方向盘（调 publish/subscribe）。

一句话定义：PubSubClient（by Nick O'Leary）是 Arduino 上最常用的 MQTT 客户端库，把 TCP 连接、MQTT 握手、心跳保活、订阅分发都封装好，我们只需 setServer、connect、publish、subscribe。

例子：client.setServer("broker.emqx.io", 1883); 一句就指定了 Broker 地址和端口。

5. 回调函数（callback）：「别人替你调用」的函数

生活类比：你在快递柜留了手机号——包裹到了，快递柜（Broker）会自动打你电话（调你的 callback），你不用一直盯着柜子看。回调就是「事件发生时，系统替你调用的函数」。

一句话定义：client.setCallback(callback) 把一个函数注册给 PubSubClient；每当有订阅消息到达，库自动调用这个函数，把 topic 和 payload 传进来。

例子：在 callback 里把收到的 payload 打印到串口——手机发 "on"，ESP32 串口立刻打印「收到主题 [esp32/cmd]：on」。

6. MQTT 在协议栈里的位置：应用层坐在 TCP 肩膀上

生活类比：上一课我们画过 TCP/IP 五层模型。MQTT 不是凭空来的——它是「应用层」协议，底下必须先有 TCP 传输层把数据可靠送达。你发 MQTT publish，其实是在一条已经建好的 TCP 连接上写一段 MQTT 报文。

一句话定义：按教材五层模型——WiFi 是链路层、IP 是网络层、TCP（端口 1883/8883）是传输层、MQTT 是应用层。这就是为什么代码里要先连 WiFi（拿到 IP）、PubSubClient 内部再建 TCP、最后才谈 MQTT 的 CONNECT/PUBLISH。

例子：本课 client.setServer("broker.emqx.io", 1883) 里的 1883 就是 TCP 端口号；MQTT 自己不解决「怎么把字节可靠送到 Broker」，那是 TCP 干的活——这也解释了为什么 MQTT 必须先跑在 TCP 之上。

三、原理介绍

MQTT 是为 IoT 设计的「发布/订阅」协议：设备之间不直接对话，全部经过一台中间服务器 Broker 中转。你 publish 到某个 Topic 的消息，Broker 会推给所有订阅了该 Topic 的设备。设备因此完全解耦——ESP32 不用知道手机的 IP，手机也不用知道 ESP32 在哪。

一条指令从手机到 ESP32 的链路：手机 publish → Broker 按 Topic 路由 → Broker 推给订阅者 → PubSubClient 收包进缓冲 → 你的 callback 被调用。

原理 1：MQTT 报文——CONNECT/SUBSCRIBE/PUBLISH 各在干什么

MQTT 跑在 TCP 之上，每种动作都是一条固定格式的报文：

  • CONNECT：connect() 发出，带唯一 ClientID——Broker 发现两个设备用同一个 ID，会把旧的踢下线，这就是「ClientID 必须唯一」的原因。
  • SUBSCRIBE：subscribe() 发出，告诉 Broker「这个 Topic 的消息推给我」。
  • PUBLISH：publish() 发出，把消息发到指定 Topic。
  • PINGREQ/PINGRESP：心跳，按 keepAlive 间隔收发，Broker 靠它判断设备还活着没——超时没心跳就把你离线。

原理 2：QoS 0/1/2——消息「最多一次 / 至少一次 / 恰好一次」

发布消息时可选 QoS 等级：QoS 0 发完就忘（最快但可能丢包）；QoS 1 至少到一次（要求对方回 PUBACK，没回就重发，可能重复）；QoS 2 恰好一次（四次握手，最可靠也最贵）。ESP32 温湿度上报用 QoS 0 足够——丢一两个采样点无所谓；开关控制指令可用 QoS 1。PubSubClient 默认 QoS 0。

原理 3：client.loop() 的回调分发——为什么这一行不能漏

WiFi 收到的 MQTT 报文先由协议栈放进缓冲区。client.loop() 每调一次，就去缓冲区取一条报文、解析它：如果是 PUBLISH，就调用你注册的 callback(topic, payload, length)；同时它还会按 keepAlive 周期发出心跳 PING。不调 client.loop() = 收不到任何下行消息，心跳也没人发，几十秒后 Broker 判定你掉线。这就是为什么它不是「可选清理」，而是 MQTT 的心脏。

Broker 说明 本课使用公共测试 Broker broker.emqx.io（端口 1883），任何人都能在上面收发消息，不要传任何敏感数据。生产环境请自建 EMQX / Mosquitto 并开启用户名密码与 TLS（8883 端口）。
记忆点：MQTT=Broker 中转的发布/订阅；CONNECT 带唯一 ClientID（重名互踢）；心跳=keepAlive 周期 PING；QoS 0/1/2=最多/至少/恰好一次；client.loop()=收包+分发回调+发心跳，必须每圈都调。

五、完整代码

先在「项目 → 加载库 → 管理库」中搜索并安装 PubSubClient（作者 Nick O'Leary）。WiFi 名称密码为示例值，必须替换。

/* ESP32 连接公共 MQTT Broker，发布 + 订阅（零基础注释版） */
#include <WiFi.h>
#include <PubSubClient.h>

const char* ssid       = "YourWiFiName";
const char* password    = "YourWiFiPassword";
const char* mqttServer  = "broker.emqx.io";   // 公共测试 Broker
const int   mqttPort    = 1883;                // 非加密端口

WiFiClient   espClient;
PubSubClient client(espClient);                 // 把 WiFiClient 包进 PubSubClient

// 收到订阅消息时自动回调（不是你手动调用，是库替你调）
void callback(char* topic, byte* payload, unsigned int length) {
  Serial.print("收到主题 [");
  Serial.print(topic);
  Serial.print("]：");
  for (unsigned int i = 0; i < length; i++) {
    Serial.print((char)payload[i]);              // 逐字节转字符打印
  }
  Serial.println();
}

// 断线自动重连
void reconnect() {
  while (!client.connected()) {
    Serial.print("正在连接 MQTT ...");
    if (client.connect("esp32-client-01")) {    // 客户端 ID 必须唯一
      Serial.println("已连接");
      client.subscribe("esp32/cmd");            // 订阅下行指令
    } else {
      Serial.print("失败，state=");
      Serial.print(client.state());
      delay(2000);
    }
  }
}

void setup() {
  Serial.begin(115200);
  WiFi.begin(ssid, password);
  while (WiFi.status() != WL_CONNECTED) { delay(500); Serial.print("."); }
  Serial.println(WiFi.localIP());

  client.setServer(mqttServer, mqttPort);       // 指定 Broker
  client.setCallback(callback);                  // 注册消息回调
}

void loop() {
  if (!client.connected()) reconnect();         // 断线就重连
  client.loop();                                 // 必须周期性调用，维持心跳+收消息

  static unsigned long last = 0;
  if (millis() - last > 5000) {                  // 每 5 秒上报一次
    last = millis();
    client.publish("esp32/test", "hello from esp32");
    Serial.println("已发布 esp32/test");
  }
}

第二个实例：一条回调处理多个订阅主题——主程序只订阅了一个 cmd 主题，这个变体演示「按 topic 分支处理」，新增一个配置主题 esp32/cfg：把主程序的 callback 整段换成下面这版，并在 setup 的 subscribe 后多加一行订阅：

/* MQTT 变体：回调里按主题分支 */
const int LED_PIN = 2;

void callback(char* topic, byte* payload, unsigned int length) {
  String msg = "";
  for (unsigned int i = 0; i < length; i++) msg += (char)payload[i];

  if (String(topic) == "esp32/cmd") {          /* 控制主题 */
    if (msg == "on")  digitalWrite(LED_PIN, HIGH);
    if (msg == "off") digitalWrite(LED_PIN, LOW);
    Serial.print("控制指令: "); Serial.println(msg);
  } else if (String(topic) == "esp32/cfg") {    /* 新增：配置主题 */
    Serial.print("收到配置: "); Serial.println(msg);
  }
}

/* setup() 里订阅两行（主程序只有第一行）：
   client.subscribe("esp32/cmd");
   client.subscribe("esp32/cfg");    // 新增订阅的主题 */

想换自己的主题？把 esp32/test 和 esp32/cmd 改成带你名字的字符串（如 ljb/test），避免和公共 Broker 上其他人撞车。

六、代码逐段讲解

第 1 段：头文件与常量（第 2~11 行）

在做什么： 引入 WiFi 和 PubSubClient 库，定义 WiFi 账号、Broker 地址端口，并创建 WiFiClient 与 PubSubClient 两个对象。

为什么这么写： PubSubClient 不直接管 WiFi，它需要一个 WiFiClient 做底层 TCP 通道——所以先建 espClient，再包进 client。

不写会怎样： 漏 WiFiClient，编译不过；Broker 地址写错，state 一直是 -2（连不上）。

第 2 段：回调函数 callback（第 13~22 行）

在做什么： 定义一个函数，把收到的 topic 和 payload 逐字节打印到串口。

为什么这么写： 这个函数不是你在 loop 里调的，而是库在收到消息时自动调——所以它的函数签名（参数个数类型）必须和库要求一致：void (*)(char*, byte*, unsigned int)。

不写会怎样： 不注册 callback，订阅到的消息会被库吞掉，你完全看不到下行数据。

第 3 段：reconnect() 断线重连（第 25~37 行）

在做什么： 只要 client 没连上，就循环尝试 connect；成功后立刻 subscribe 一次（因为订阅信息不会跨重连保留）。

为什么这么写： WiFi 抖动、Broker 重启都会导致断线；如果不主动重连，ESP32 就永远离线。subscribe 放在 reconnect 里是关键——很多新手断线后收不到指令，就是因为重连后忘了重新订阅。

不写会怎样： 漏 subscribe，连上了也收不到 esp32/cmd 的下行消息。

第 4 段：setup() 初始化（第 39~49 行）

在做什么： 先连 WiFi（等 WL_CONNECTED），再 setServer 指定 Broker，setCallback 注册回调。

为什么这么写： 顺序不能乱——没网就设 Broker 没用；setCallback 必须在 connect 之前注册。

不写会怎样： 漏 setCallback，消息到达时没有处理函数；顺序颠倒可能导致第一轮消息丢失。

第 5 段：loop() 维持连接并上报（第 51~62 行）

在做什么： 每轮先看是否连接、断了就重连；然后调 client.loop() 喂库心跳；用 millis() 非阻塞地每 5 秒 publish 一次。

为什么这么写： client.loop() 是 PubSubClient 的「心跳泵」，不调的话 Broker 30 秒后会把你踢下线；millis() 代替 delay(5000) 是为了不阻塞接收下行消息。

不写会怎样： 漏 client.loop()，连接几秒就被 Broker 断开；用 delay(5000) 会导致这 5 秒内下行指令收不到。

七、现象演示说明

  • 现象 1：串口先打印 WiFi IP，随后打印「正在连接 MQTT ...已连接」。
  • 现象 2：每 5 秒打印一行「已发布 esp32/test」。
  • 现象 3（验证上行）：电脑下载 MQTTX 等工具，新建连接填 broker.emqx.io:1883，订阅 esp32/test，应能每隔 5 秒收到 "hello from esp32"。
  • 现象 4（验证下行）：在 MQTTX 向 esp32/cmd 发布任意字符串（如 "on"），ESP32 串口立刻打印「收到主题 [esp32/cmd]：on」。

可量化的验证方法：

  • 数上报间隔：MQTTX 收到的两条消息间隔应约为 5 秒（millis() 判断 >5000 决定）。
  • 断开 WiFi 测试：暂时关掉路由器，ESP32 串口应打印 state=... 并在恢复后自动重连、继续上报。
  • 改主题：把 publish 主题改成 esp32/test2，MQTTX 订阅 esp32/test 就收不到了——验证 Topic 是精确匹配的。
