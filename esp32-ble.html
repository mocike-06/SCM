BLE 低功耗蓝牙与 GATT

系列：ESP32 进阶 更新：2026-10-25

上一课用经典蓝牙（SPP）实现了串口透传。但手环、温湿度计、门锁……现代 IoT 设备几乎都用 BLE（低功耗蓝牙）：连一次电能用半年。本课讲透 BLE 的广播/连接模型和 GATT 数据模型，用 ESP32 做个「BLE UART 透传」，手机 App 和开发板互发文字——这是蓝牙遥控器的 BLE 版基础。

一、本课目标与前置知识

学完本课你能做到：

  • 分清经典蓝牙（SPP）与 BLE 的差别，知道什么时候用哪个。
  • 说出 GATT 模型：服务（Service）→ 特征（Characteristic）→ UUID，数据怎么组织。
  • 用 nRF Connect 手机 App 连接 ESP32，双向收发字符串。

需要提前掌握的前置知识（对应学习路线阶段 5）：

  • 经典蓝牙（esp32-bluetooth.html）：已有「手机 ↔ ESP32」配对通信经验。
  • 串口（esp32-bluetooth.html / stm32-usart.html）：透传 = 无线版串口。
  • 本课与 I2C（esp32-i2c.html）无依赖，可并行学。

本课会出现的新名词：BLE、广播（Advertising）、连接（Connection）、GATT、Service、Characteristic、UUID、Notify、透传、nRF Connect。

二、基础概念铺垫

1. 经典蓝牙 vs BLE：省电是头等大事

生活类比：经典蓝牙像「打电话」——建立连接后一直保持通话（持续占用链路）；BLE 像「发微信」——平时不连接、不吭声，只在有事时广播/收发一下，其余时间睡觉。

一句话定义：经典蓝牙（SPP）持续连接、速率高（可达 1~2Mbps）、适合音频和连续数据传输；BLE 以「极低功耗」为核心，支持广播发现、按需连接、几十 ms 完成一次小数据收发，一颗纽扣电池能用数月——IoT 传感器首选。

例子：蓝牙音箱用经典蓝牙（连续音频流）；温湿度计用 BLE（每 10 分钟报一次数）。ESP32 两种都支持。

2. 广播与连接：先「吆喝」再「握手」

一句话定义：BLE 设备默认 广播：周期性在 37/38/39 三个信道发出自己的名称和能力（如「MyBLE_Device」）；手机扫描到后发起 连接，建立后进入低功耗连接状态（两设备按约定间隔醒来交换数据）。

例子：nRF Connect 里能搜到「ESP32_BLE_UART」这个名字——那是广播包里带的服务名；点击 connect 即建立连接。

3. GATT：BLE 的数据「图书馆」

生活类比：GATT 把设备数据组织得像图书馆：服务（Service）= 一个书架（如「温度服务」），特征（Characteristic）= 书架上的书（如「当前温度」），每本书有唯一编号 UUID。手机要读温度，就按「书架号 + 书号」去取。

一句话定义：GATT（通用属性协议）定义 BLE 数据的组织方式：设备暴露若干 Service，每个 Service 含若干 Characteristic（最小数据单元），每个都用 16 位或 128 位 UUID 标识。读、写、订阅（Notify）都作用在 Characteristic 上。

例子：本课用的 Nordic UART 服务（NUS，服务 UUID 6E400001-…）里有两个特征：写通道 6E400002（手机→设备发数据）、Notify 通道 6E400003（设备→手机推数据）。

4. Notify：设备主动「推送」而不是等手机来问

一句话定义：Notify（通知）让设备在数据变化时主动把值推给手机（手机先订阅该特征）。相比手机轮询读，Notify 实时且省电——传感器上报的标准姿势。

例子：设备每 1 秒通过 Notify 推一次温湿度，手机 App 实时刷新，无需请求。

5. GAP 与 GATT：BLE 的两员大将

生活类比：GAP 像「门口保安」——负责谁能靠近、怎么广播、怎么配对进门；GATT 像「图书馆管理员」——进门之后，数据按书架/书号怎么取。一个管「连上之前」，一个管「连上之后」。

一句话定义：BLE 两大核心协议——GAP（通用访问协议）管广播、扫描、连接、断开（决定设备能不能被发现、能不能连上）；GATT（通用属性协议）管连上之后的数据组织（Service/Characteristic/UUID，决定数据怎么读写）。本课「startAdvertising」是 GAP，「createService/createCharacteristic」是 GATT。

例子：手机搜不到设备，问题出在 GAP（广播没开/权限）；能连上但读写不到数据，问题出在 GATT（UUID/属性错）——排障先分清是 GAP 层还是 GATT 层。

三、原理介绍：BLE UART 透传的数据流

BLE（低功耗蓝牙）和经典蓝牙是两套完全不同的协议：经典蓝牙像「一直挂电话」，BLE 像「平时睡觉、有事发个微信」。理解它「广播→连接→按 GATT 表收发」的模型，才能搞懂为什么需要服务/特征值/UUID 这套绕口令。

一次 BLE 透传的链路：ESP32 广播 → 手机扫描连接 → 手机读 GATT 表找到服务和特征 → 写特征上行 / Notify 特征下行。

原理 1：BLE 为什么省电——广播与连接间隔

未连接时，BLE 设备每隔几百 ms 在 3 个广播信道上喊一声自己的名字，其余时间全睡——平均电流微安级。一旦手机连接，双方约定一个连接间隔（比如每 50ms 一起醒来交换一次数据），其余时间依然睡觉。对比经典蓝牙 SPP 一直保持链路通电，这就是「一颗纽扣电池用半年」的物理基础。代价：数据是小包、有延迟——所以 BLE 传不了音频，只适合传感器上报和开关指令。

原理 2：GATT 分层——Server / Service / Characteristic / UUID

连上之后，数据怎么组织由 GATT 协议规定，分四层：

  • Server（设备）：ESP32 整台设备就是一个 GATT Server。
  • Service（服务）：一组相关功能的集合，本课用 Nordic UART Service（UUID 6E400001）。
  • Characteristic（特征值）：服务里的具体数据点，本课两个：6E400002（手机→设备写）、6E400003（设备→手机 Notify）。
  • UUID：每个 Service/Characteristic 的唯一编号——手机靠 UUID 找到「往哪个特征写、从哪个特征收」。

nRF Connect 里你看到的就是这棵树：一个服务展开两个特征值。注意：0xFFE0/0xFFE1 是 HM-10 模块用的另一组短 UUID，不是 NUS——别混淆。

原理 3：写回调与 Notify——手机怎么收设备的数据

两个方向走两套机制：手机→设备是「写」——手机往 6E400002 写字节，ESP32 注册的 onWrite 回调被自动调用，在回调里读值打印。设备→手机是「Notify（通知）」——ESP32 调 setValue + notify() 把值推出去，但前提是手机先往该特征的 CCCD 描述符写 1 订阅（没订阅，notify 发了手机也收不到——这就是 nRF Connect 里要先点那个「↓」订阅的原因）。

记忆点：BLE=平时睡、按连接间隔醒来交换（微安级）；GATT 四层=Server→Service→Characteristic→UUID；上行=手机写特征（触发 onWrite 回调）；下行=Notify 推送，手机必须先订阅 CCCD；小包低延迟，不适合音频。

四、硬件接线说明

BLE 在芯片内部射频，无需接线。本课硬件只需：

设备说明
ESP32 开发板USB 供电 + 串口监控
手机安装 nRF Connect（Android/iOS 均有）
（可选）LEDGPIO2 板载 LED，验证手机指令控制

为什么演示不需要任何外设：BLE 是无线射频，天线上板载——「串口监控 + 手机 App」就是全部装备。手机和 ESP32 距离 10 米内即可。

避坑 某些手机 App 需要位置权限才能扫描 BLE（Android 上 BLE 扫描归「位置」权限管）——nRF Connect 首次使用会弹权限，全部允许，否则扫描不到任何设备。

五、完整代码

需要安装 ESP32 BLE Arduino 库（库管理器搜索安装）。示例：BLE UART 透传 + 指令控灯。

BLE UART 透传 + LED 控制

/* BLE UART：手机 ↔ ESP32 双向收发；收到 "ON"/"OFF" 控制板载 LED */
#include <BLEDevice.h>
#include <BLEServer.h>
#include <BLEUtils.h>
#include <BLE2902.h>

#define SERVICE_UUID        "6E400001-B5A3-F393-E0A9-E50E24DCCA9E"  // Nordic UART Service
#define CHAR_RX_UUID        "6E400002-B5A3-F393-E0A9-E50E24DCCA9E"  // 手机→设备（写）
#define CHAR_TX_UUID        "6E400003-B5A3-F393-E0A9-E50E24DCCA9E"  // 设备→手机（Notify）

BLECharacteristic *pTxChar;
bool deviceConnected = false;

/* 连接状态回调 */
class MyServerCallbacks : public BLEServerCallbacks {
  void onConnect(BLEServer *s)    { deviceConnected = true;  Serial.println("Connected"); }
  void onDisconnect(BLEServer *s) { deviceConnected = false; Serial.println("Disconnected");
                                     BLEDevice::startAdvertising();  /* 断开后重新广播 */
                                   }
};

/* 手机写数据回调 */
class MyCallbacks : public BLECharacteristicCallbacks {
  void onWrite(BLECharacteristic *pChar) {
    std::string value = pChar->getValue();
    if (value.length() > 0) {
      Serial.print("RX: ");
      Serial.println(value.c_str());

      /* 指令控制：收到 ON/OFF 翻转板载 LED */
      if (value == "ON")  digitalWrite(2, HIGH);
      if (value == "OFF") digitalWrite(2, LOW);
    }
  }
};

void setup() {
  Serial.begin(115200);
  pinMode(2, OUTPUT);

  /* 初始化 BLE */
  BLEDevice::init("ESP32_BLE_UART");           // 广播名称
  BLEServer *server = BLEDevice::createServer();
  server->setCallbacks(new MyServerCallbacks());

  /* 建服务 + 两个特征 */
  BLEService *service = server->createService(SERVICE_UUID);

  pTxChar = service->createCharacteristic(
              CHAR_TX_UUID, BLECharacteristic::PROPERTY_NOTIFY);
  pTxChar->addDescriptor(new BLE2902());        // Notify 必须加 2902 描述符

  BLECharacteristic *pRxChar = service->createCharacteristic(
              CHAR_RX_UUID, BLECharacteristic::PROPERTY_WRITE);
  pRxChar->setCallbacks(new MyCallbacks());

  service->start();
  BLEDevice::startAdvertising();
  Serial.println("BLE UART ready");
}

void loop() {
  /* 设备→手机：每 2 秒 Notify 推送一次时间戳 */
  if (deviceConnected) {
    char buf[32];
    sprintf(buf, "tick=%lu", (unsigned long)millis());
    pTxChar->setValue(buf);
    pTxChar->notify();                          // 推送（需手机先订阅）
  }
  delay(2000);
}

第二个实例：再加一个「读特征」，手机随时读 ESP32 状态——主程序只有写/Notify 两个特征，这个片段演示如何补一个手机主动读的状态特征（加在主程序建服务之后、loop 之前）：

/* BLE 变体：新增只读特征（手机读它拿设备状态） */
BLECharacteristic *pStatusChar;

/* 在主程序 pService->createCharacteristic(...) 之后加： */
pStatusChar = pService->createCharacteristic(
      BLEUUID((uint16_t)0x2A18),                 // 标准特征 UUID，可自定
      BLECharacteristic::PROPERTY_READ);          // 只读属性
pStatusChar->setValue("ESP32 alive");

/* 在 loop() 的 notify 旁，每次循环刷新读数： */
char st[24];
sprintf(st, "uptime=%lus", (unsigned long)(millis()/1000));
pStatusChar->setValue(st);
/* 手机在 nRF Connect 里点这个特征的 Read，就能看到已运行秒数 */

六、代码逐段讲解

第一段：UUID 与三个组件的关系

SERVICE_UUID 标识整个服务；CHAR_RX_UUID 是手机写给设备的「收件箱」；CHAR_TX_UUID 是设备推给手机的「发件箱」。为什么用这么长的 UUID：128 位 UUID 全球唯一、避免和标准服务冲突；16 位短 UUID（如 0xFFE1）是标准预分配。规则：一个服务里可以有好几个特征，各管一件事——收发分两个特征是 BLE UART 的惯例。

第二段：setValue 与 notify 的推送链路

pTxChar->setValue(buf) 把字符串放进特征值缓存，notify() 把它广播给已订阅的手机。为什么必须加 BLE2902 描述符：Notify 属性要求配 CCCD（客户端特征配置描述符，UUID 0x2902），没有它手机无法完成「订阅」操作——这是新手最常见的「能连上但收不到通知」的原因。

第三段：onWrite 回调与字符串比较

手机写数据时 onWrite 被调用，getValue() 取出字节流。为什么用 == 比较而不是逐个字节：std::string 直接支持内容比较，代码最简洁。为什么 Serial.print 收尾要 println：方便串口监视器看完整一行。指令解析从这里扩展：改成 switch 多指令，就是遥控器协议。

第四段：断开重连与重广播

onDisconnect 里调用 BLEDevice::startAdvertising()——BLE 设备连接断开后不会自动回到广播状态，必须手动重启广播，否则手机再也扫不到它。这是从 demo 到产品的关键细节：任何断开都要处理重连逻辑。

七、现象演示与验证

  • 发现：nRF Connect 扫描到 ESP32_BLE_UART，点 Connect 显示 Connected。
  • 上行：在 0x6E400002 特征写 hello，串口打印 RX: hello；写 ON/OFF 板载 LED 亮/灭。
  • 下行：订阅 0x6E400003 的 Notify，App 每 2 秒收到 tick=xxxx。

验证方法：

  1. 连接状态断开 ESP32 电源再上电——观察 App 端断开提示与重新广播（1~2 秒后又能扫到）。
  2. 不订阅 Notify 直接看 0x6E400003——读不到推送值，订阅后才出现——理解 CCCD 订阅机制。
  3. 把 BLEDevice::init("ESP32_BLE_UART") 改成别的名字，App 搜索新名字——验证广播名称由 init 决定。

九、课后练习与延伸

练习 1（必做）：把「ON/OFF」指令升级为「数值调光」：手机发 D:128，ESP32 解析出占空比控制 LED 亮度（结合 esp32-pwm.html）。
